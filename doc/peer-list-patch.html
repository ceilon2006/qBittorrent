Filters

  • IPv4 / IPv6 hide or show rows of that address family. At least one stays checked: unchecking the last one checks it again.
  • Seen in the last: 1 hour / 6 hours / 24 hours / 7 days hides peers whose Last seen is older. Connected peers are always shown, because they are active now.
  • Both choices are remembered (settings keys PeerListDialog/ShowIPv4, PeerListDialog/ShowIPv6, PeerListDialog/SeenWithinHours).
  • The summary line counts only the rows that are shown. Sorting by any column keeps the filter correct.

3. How peers are collected

libtorrent's public API only lists peers you are connected to. It keeps its own list of other known peers internally, but does not hand it out (the old get_full_peer_list is deprecated and internal). The patch therefore collects peers itself, as libtorrent reports them, into a per-torrent store called the peer book.

Source 1

on_add_peer

A libtorrent plugin hook, called every time a tracker, DHT, PeX, LSD or resume data reports a peer, including peers the IP filter refuses (flag filtered). qBittorrent's own torrent plugin (NativeTorrentExtension) now overrides it. Runs on libtorrent's network thread.

Source 2

peer_blocked_alert

Sent when libtorrent refuses a peer, with one of eight reasons. Adds the exact reason, and records refusals that never went through on_add_peer.

Source 3

peer_connect / peer_disconnected

Connection results. A failure while a connection is being set up marks the peer Unreachable; a successful outgoing connection clears that.

Source 4

Live peer info

When the dialog refreshes, it asks libtorrent for the connected peers (same as the Peers tab) and merges them by IP and port.

This is different from the separate qt-libtorrent_peer_collector tool, which sends its own HTTP/UDP announces to trackers to read their peer lists. The fork needs no extra announces: it uses what libtorrent's normal announces already deliver, so there is no additional tracker traffic.

The peer book is shared between libtorrent's network thread (writing) and the GUI thread (reading), so every access takes a mutex. Entries are keyed by torrent and IP|port.

6. Unreachable: when and why

A peer becomes Unreachable when

  1. An outgoing connection fails while it is being set up. libtorrent reports a disconnect whose operation is connect, sock_open, sock_bind or sock_bind_to_device. The error and the socket type go into the Reason column:
    Reason textUsual cause
    Connection timed out / timed outThe peer does not answer: offline, or a firewall or NAT silently drops the attempt
    Connection refusedThe machine answers, but nothing listens on that port
    Network is unreachable / No route to hostNo route to that address from your network
    Operation not supportedThis machine cannot use that address family, e.g. public IPv6 peers on a machine without a global IPv6 address
    Example: Operation not supported (μTP), Connection timed out (TCP).
  2. libtorrent refuses the connection with invalid_local_interface: no local interface can reach the address.

It does not become Unreachable when

  • the peer is already Blocked or This machine;
  • a connection was made and later closed (End of file, Connection reset by peer, upload to upload connection): that peer was reachable;
  • libtorrent has not tried the peer yet: that is Not connected.

It stops being Unreachable when

  • an outgoing connection to it succeeds later;
  • you change the IP filter: it returns to Not connected, or becomes Blocked if the new filter refuses it;
  • it expires (7 days without a report) or qBittorrent restarts.

It stays Unreachable even when

  • trackers or DHT report it again (on purpose: otherwise the state would flip on every report);
  • the peer connects to you (incoming). A peer behind NAT connects from a random source port, not the listening port the tracker reported, so the incoming connection cannot be matched to the stored row. The dialog then shows two rows: the stored one Unreachable, and a live Connected, Source: Incoming row while the connection lasts.

libtorrent often tries μTP first. If that attempt fails, the row says so (… (μTP)) even when a later TCP attempt might work; a successful TCP connection clears it.

7. This machine

libtorrent sometimes hears about the computer it runs on:

  • LSD (Local Peer Discovery) announces the torrent on the local network, including over IPv6 link-local, and the client picks up its own announcement. On the test VM this produced fe80::fe7f:9046:74f4:ee36%ens33, source LSD.
  • Trackers often return the announcing client's own public address in the peer list.

libtorrent refuses to connect to itself and marks such a report as filtered, even with no IP filter loaded. Without special handling it would appear as Blocked — IP filter, which is misleading.

The patch keeps a list of this machine's addresses: every network interface address (IPv6 link-local included) plus the external IPv4 and IPv6 addresses qBittorrent has detected. It is refreshed every 10 minutes and whenever the external IP changes. IPv6 scope (%ens33) is ignored when comparing, and IPv4-mapped IPv6 is treated as IPv4. Matching rows show This machine, are never counted as blocked, and are not touched by filter changes.

Turning off LSD (Options → BitTorrent → Enable Local Peer Discovery) removes the LSD case entirely; LSD only finds peers on your own LAN.

8. How long a peer stays listed

EventEffect
Reported again (tracker, DHT, PeX, LSD)Last seen is reset; the 7 days start over
Not reported for 7 daysRemoved by the cleanup that runs every 10 minutes (SEEN_PEER_EXPIRY_SECS)
qBittorrent restartsEverything is lost: the peer book is kept only in memory, never written to disk
Torrent removedThat torrent's entries are deleted
50,000 entries reached for one torrentNo new entries for that torrent; existing ones stay (MAX_PEERS_PER_TORRENT)
IP filter changedNothing is removed; states are re-checked (next section)
Incoming-only connected peersNot stored; visible only while connected

Why 7 days. An active peer in a small swarm is reported again within one or two announce rounds (trackers usually every ~30 minutes). In a large swarm, trackers return only a random sample, so an active peer can go unreported for hours; a short limit would drop peers that are still there. For a view of the swarm right now, use Seen in the last: 1 or 6 hours; the 7 days serve as history.

Last seen ≠ last active. It is the last time your client heard of the peer. A recent value means it is almost certainly still in the swarm; an old one means it has probably left, but not certainly.

Saving to disk was considered and left out: after a restart the list refills from trackers and DHT within an announce round or two, automatic saving would need per-torrent files and re-matching at startup, and it would keep IP history on disk. A manual Save… button would be the simpler option if ever needed.

9. IP filter changes and reannounce

The problem in standard qBittorrent

  1. While a peer is refused, libtorrent does not keep it: it drops it from the torrent's peer list.
  2. When you change the filter to allow such peers, libtorrent does not look for the peers it dropped.
  3. They come back only with the next announce. Force reannounce does not help: qBittorrent calls it without libtorrent's ignore_min_interval flag, so the announce is held until the tracker's minimum interval (often 15–30 min) has passed.
  4. Stopping and starting the torrent works, because a fresh start is not subject to the minimum interval.

What the fork does when the filter really changes

  1. The new filter's rules are compared with the previous ones. Nothing happens if they are identical (e.g. the reload button on an unchanged file), and nothing happens for the first filter at startup.
  2. Every peer in the peer book is re-checked: peers the new filter refuses become Blocked — IP filter; all others lose any earlier refusal (filter, settings or Unreachable) and return to Not connected, so libtorrent's next attempt decides their state again. This machine rows are left alone.
  3. Every running torrent (not stopped, not queued) reannounces to all trackers ignoring the minimum interval and announces to DHT.
  4. The log shows IP filter changed. Cleared the blocked peers list and reannounced running torrents. Torrents: N. The wording is older than the re-check in step 2: nothing is cleared any more, the list is re-checked.

Ban peer permanently only adds a block and goes a different way in qBittorrent, so it does not trigger a reannounce.

Do not reload a changed filter many times in a row: each change makes every running torrent contact its trackers immediately, and some trackers penalise clients that ignore their minimum interval too often.

10. Filter file formats and IPv6

qBittorrent picks the parser by file extension. IPv6 ranges work only in .dat:

FileLineqBittorrent 5.2.4
.p2pBlocked-2:::-ffff:ffff:ffff:ffff:ffff:ffff:ffff:ffffmalformed
.p2pBlocked-2:0:0:0:0:0:0:0:0-ffff:…:ffffmalformed
.p2pBlocked-3:[::]-[ffff:…:ffff], all ipv6:::/0malformed
.dat::-ffff:ffff:ffff:ffff:ffff:ffff:ffff:ffffapplied
.dat:: - ffff:…:ffff , 0 , all IPv6applied

Why: a .p2p line is label:start-end, and qBittorrent ends the label at the last : so labels may contain colons. Every IPv6 address contains :, so the line is always cut in the wrong place. The .p2p (PeerGuardian) format is IPv4 by design.

Your filter generator (qt-p2p_filter_generator, commit 4fda24d) has a Block all IPv6 addresses (bare ranges only) checkbox that appends the .dat line above. It is disabled while PeerGuardian labels are on. Save the output as ipfilter.dat without labels and load that in qBittorrent.

A filter with only IPv4 ranges lets every IPv6 peer through. On a machine without global IPv6 those peers still cannot connect; they show as Unreachable — Operation not supported.

11. Behaviour worth knowing

  • One peer, two rows (NAT). A peer behind NAT that connects to you appears as a live Connected, Source: Incoming row (random source port) next to its stored row (listening port, from the tracker). When the incoming connection closes, the live row disappears after the next Refresh. The stored row usually stays Not connected: libtorrent does not open a second connection to an IP it is already connected to (allow_multiple_connections_per_ip is off by default), and after a disconnect it waits before retrying old peers.
  • Connections come and go. Normal BitTorrent behaviour: both sides seeding (upload to upload connection), connection limits, idle timeouts, peers leaving.
  • Refused incoming connections without a torrent. When a blocked peer connects to you, libtorrent refuses it before it knows which torrent it wants. It goes to the peer log only, not to any torrent's list.
  • Bans are separate. libtorrent's smart-ban of peers that send corrupt data is a different event and is not shown as Blocked.
  • IP column sorts as text. IPv4 and IPv6 interleave (2a02:… sorts between 212.… addresses); use the IPv4/IPv6 checkboxes instead.
  • Snapshot. The dialog does not refresh on its own.

12. Performance cost

  • Connect alerts: one alert per connection opened and one per connection closed or failed. qBittorrent allows at most 30 new connection attempts per second (ConnectionSpeed default), so at most about 60 extra alerts per second, mostly right after a torrent starts. libtorrent's alert queue is set practically unlimited by qBittorrent (alert_queue_size = INT_MAX / 2), so nothing is dropped. A 90-second test run logged no dropped alerts.
  • Per report or alert: one mutex lock and one hash lookup.
  • Memory: at most 50,000 entries per torrent, a few MB.
  • Network: no extra traffic, except the reannounce after a real IP filter change.

Connection tracking is not configurable; the cost was judged too small to need a switch.

14. Building and running

On Kubuntu 26.04, besides the usual qBittorrent build dependencies, two packages were missing:

sudo apt install qt6-tools-dev qt6-base-private-dev

Build and run from the repository folder:

cmake -G Ninja -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
./build/qbittorrent

After code changes, cmake --build build is enough. Quit a running qBittorrent with File → Exit before starting the new build, otherwise the old instance keeps running. To test without touching your real settings and torrents: ./build/qbittorrent --profile="$HOME/qbt-test".

Git remotes: origin = upstream qBittorrent (fetch new releases), myrepo = git@github.com:ceilon2006/qBittorrent.git (your branch).
